# Локальная работа и будущий VPS

Сейчас сервер не требуется: приложение по-прежнему запускается через `bin/rails server` в development. Настройки HTTPS действуют только в production.

## Изменение существующей базы

Перед первой миграцией этой версии сделайте резервную копию. Новая миграция добавляет только поля снимков правил и балансов; существующие записи не удаляет. Старые применённые миграции не изменялись.

```bash
bundle exec ruby bin/backup --environment development --destination "$HOME/forecast-backups"
bin/rails db:migrate
```

Снимок правил сохраняется при первом подтверждении результата и используется при повторном расчёте после отката. Для старых подтверждённых результатов без снимка исторические настройки автоматически восстановить невозможно. Перед пересчётом таких матчей администратор должен установить согласованные правила; прежние сохранённые очки сами не изменяются.

Откат полностью отменяется, если после него баланс участника не покрывает сохранённые ставки. Сообщение указывает участника. Не меняйте чужие ставки: сначала проверьте связанные операции и при необходимости выполните обоснованную ручную корректировку ЗБ с причиной, затем повторите откат.

## Резервное копирование SQLite

`bin/backup` использует SQLite Online Backup API, учитывает WAL и проверяет целостность каждой копии. Скрипт не запускает Rails, миграции или seeds, не удаляет старые копии. Каталог назначения должен находиться вне `storage` и вне репозитория. Результат — отдельный закрытый каталог с базами и SHA-256 manifest.

```bash
bundle exec ruby bin/backup --environment development --destination "$HOME/forecast-backups"
# На будущем сервере:
bundle exec ruby bin/backup --environment production --destination /private/forecast-backups
```

Основные игровые данные находятся в одной primary-базе. В production дополнительно копируются базы cache, queue и cable. Копирование нескольких баз не является общей транзакцией: для согласованного снимка всех четырёх остановите веб-процесс и фоновые задания на время копирования. Скрипт сохраняет SQLite, а файлы загрузок Active Storage и master key нужно резервировать отдельно в защищённом хранилище. Копии содержат персональные данные: храните их вне Git, шифруйте при переносе и регулярно отправляйте на другой носитель/сервер. Рекомендуемая частота — ежедневно и перед миграциями; срок хранения определяет владелец. Автоматическое удаление копий не настроено.

## Проверка восстановления

```bash
bundle exec ruby bin/restore-backup /private/forecast-backups/ИМЯ_КОПИИ /private/restore-check-НОВЫЙ_КАТАЛОГ
```

Проверяются manifest, SHA-256 и `PRAGMA integrity_check`. Назначение должно отсутствовать: существующие каталоги и рабочие базы скрипт не перезаписывает. После проверки выполните пробный запуск приложения на изолированной копии и проверьте таблицу, прогнозы и баланс. Возврат копии на рабочее место выполняет владелец отдельно при остановленных web/worker; автоматической замены данных нет.

## Подготовка VPS

Когда появится сервер, нужны DNS-домен, VPS с Docker и постоянным диском, SSH-доступ и Docker registry. Для `config/deploy.yml` задайте в текущем окружении, не коммитя секреты:

- `APP_HOST`: домен без протокола, например `forecast.example.org`;
- `DEPLOY_HOST`: IP/имя VPS;
- `DEPLOY_USER`: SSH-пользователь с доступом к Docker;
- `DEPLOY_IMAGE`: имя образа с namespace, например `owner/forecast_bot`;
- `REGISTRY_SERVER`: registry (по умолчанию `ghcr.io`);
- `REGISTRY_USERNAME`: пользователь registry;
- `KAMAL_REGISTRY_PASSWORD`: токен с нужными правами;
- `RAILS_MASTER_KEY`: ключ существующего приложения (можно читать из локального `config/master.key`).

Kamal proxy получает HTTPS-сертификат для `APP_HOST`. Rails использует secure cookies, HTTPS и проверку Host; исключение из перенаправления и Host-проверки сделано только для `/up`. Порты 80/443 должны вести на proxy; внутренний порт Rails не публикуйте напрямую. SQLite и локальные загрузки сохраняются в постоянном томе `forecast_bot_storage`.

Перед первым размещением проверьте `bin/rails test`, `bin/rails zeitwerk:check`, `bin/rubocop`, `bin/brakeman`, затем `bin/kamal config`. Деплой — отдельная операция после готовности VPS и разрешения владельца. Эта задача не запускает деплой и не создаёт сервер.
