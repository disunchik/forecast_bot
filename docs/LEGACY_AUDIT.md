## Отличия старого сезона, которые нельзя автоматически объявлять ошибками сайта

- На листе «Топ10» итог содержит весь накопленный баланс ЗБ: например, `C4 = 101 + D4`. Проверено, что числовая база равна сумме 7 последних и 3 лучших старых результатов у всех десяти участников. В новом ТЗ ЗБ расходуются как ставка с ограниченным бонусом, а оставшийся баланс используется для тай-брейка; он не прибавляется к рейтингу целиком. Текущий Rails следует новому ТЗ.
- На листе «Результаты по последнему матчу», строки 4–6, три участника с одинаковыми итоговыми очками имеют по +1 ЗБ, хотя порядковые номера строк различны. В новом ТЗ награды +3/+2/+1 относятся к трём разным местам после всех тай-брейков. Старый срез не доказывает общее правило для всех ничьих, но показывает отличие фактической выдачи наград.
- В старых принятых прогнозах есть повтор одного футболиста внутри одного прогноза. В новом ТЗ футболист выбирается один раз, а фактически забитый им дубль учитывается расчётчиком. Это согласованное отличие, не пропущенный второй чекбокс.
- Старый бот предлагает «8 и больше», сохраняя это как 8; новый сайт принимает неотрицательный целый счёт согласно ТЗ.
- Листы старой таблицы публично показывают чужие накопленные ЗБ. Новый сайт скрывает чужие ставки и балансы от обычных пользователей по согласованному правилу.
- Старые прогнозы, таблицы, остатки лимитов и сезонные ЗБ не входят в согласованный первоначальный импорт нового сезона. Учётные записи и ранее выданные ачивки — отдельный перенос, а не автоматическое следствие загрузки кода из GitHub.

Эти отличия зафиксированы для осознанной сверки. Рабочие правила остаются в `REQUIREMENTS.md`; старый сезон не заменяет принятые решения автоматически.

## Подтверждённые ошибки и опасные административные сценарии

### A1. P1 — невозможный первый гол принимается и публикуется

Модели проверяют только совместимость «никто» с 0:0. Они не запрещают «Рома забила первой» при её нуле голов. Через сервис принимается прогноз 0:1 с первым голом Ромы; через административные HTTP-действия сохраняется и подтверждается такой же невозможный фактический результат.

В исходном боте первый гол при нуле голов одной стороны и при однозначном счёте первого тайма определяется автоматически: `handlers/forecast.py:304`. В Rails нужно проверить и FT, и однозначный HT, причём одинаково в прогнозе и фактическом результате.

Код: `app/models/forecast.rb:46`, `app/models/match_result.rb:22`.

### A2. P1 — перенос матча между сезонами после отката нарушает награды

Воспроизведение: подтвердить матч и выдать +3; откатить его; через форму администратора сменить сезон матча; активировать новый сезон, подать новый прогноз и подтвердить результат. Старые +3 правильно остаются в старом сезоне, но в новом награда равна 0: сервис считает старую выплату по тому же `match_id` уже оплаченной, не учитывая сезон.

Нужна защита исторической идентичности матча: после появления подтверждений/денежных операций запретить обычную смену сезона. Для реально другого сезона создавать другой матч. Нельзя просто перенести старые операции в новый сезон или снять сохранённые ЗБ с участника. Для допустимых переносов до появления истории синхронизировать проверки и блокировки обоих сезонов.

Код: `app/controllers/admin/matches_controller.rb:50`, `app/controllers/admin/matches_controller.rb:95`, `app/services/match_confirmation_service.rb:143`.

### A3. P2 — допустимое значение настройки 0 ломает выдачу ачивки

Админ может сохранить `achievement_normal_first = 0`; аналогичный случай возможен у других наград ачивок. При выдаче сервис пытается создать операцию ЗБ с суммой 0, которую журнал запрещает. Вся выдача откатывается: ачивка не появляется. Воспроизведён `ActiveRecord::RecordInvalid`.

Нужно согласовать допустимые значения формы и операции: либо выдавать достижение без нулевой записи в журнале, либо запрещать такую настройку с объяснением. Первый вариант сохраняет уже разрешённое в настройках значение 0.

Код: `app/models/scoring_rule.rb`, `app/models/gold_point_transaction.rb`, `app/services/gold_points_service.rb:48`.

### A4. P2 — журнал не объясняет исправления временного вопроса

Смена правильного варианта A на B записывает `match_result.update`, но `before/after` содержат только атрибуты результата и голы. Правильные варианты, принятые тексты и аннулирование отсутствуют. Для редактирования определения вопроса журнал матча также не содержит вложенного состояния вопроса. По журналу нельзя восстановить, какое именно решение изменило очки участников.

Нужно сохранять до/после для текста, типа, стоимости, вариантов с постоянными ID, правильных вариантов, принятых текстов и флага аннулирования. Для исправления после публикации использовать откат и повторное подтверждение по согласованной процедуре.

Код: `app/controllers/admin/match_results_controller.rb:19`, `app/controllers/admin/match_results_controller.rb:98`, `app/controllers/admin/matches_controller.rb:64`.

### A5. P2 — реальный импорт нельзя запускать без предварительной проверки

В старой таблице шесть разных никнеймов несовместимы с текущими ограничениями сайта: четыре из-за символов, два из-за длины. Это не предложение переименовать их автоматически. Нужна утверждённая карта старого и нового ника, при этом постоянной связью в Rails становится `user_id`.

На синтетическом файле импорт создал первую допустимую запись, затем упал на второй недопустимой: предварительной проверки всего файла и общей транзакции нет. Повторный запуск умеет пропускать существующие ники, но это не заменяет отчёт о конфликтующих аккаунтах. Дополнительно следует проверять совпадения после удаления крайних пробелов и приведения регистра, хотя в прочитанном списке таких совпадений не найдено.

Код: `lib/tasks/legacy_import.rake:7`, `app/models/user.rb`.

### A6. Требует решения по UX — опечатка после дедлайна уничтожает весь прогноз

Воспроизведено: после закрытия прогнозов изменить только текст вопроса, добавив `!`, и нажать «Сохранить матч». Все прогнозы этого матча удаляются, включая счёт, выбор футболистов и ответы; резерв возвращается. Пользователи уже не могут отправить их заново, поскольку дедлайн прошёл. Отдельного предпросмотра количества затрагиваемых прогнозов и подтверждения последствий нет.

Сброс при существенном изменении матча предусмотрен ТЗ. Здесь проблема в том, что любое изменение текста приравнивается к существенному, а интерфейс не объясняет последствия. Это отдельный административный сценарий, не ошибка сохранения неизменённого вопроса: неизменённые варианты сохраняются корректно.

Предлагаемая доработка: отделить косметическую правку от смены условий; перед сбросом показывать количество прогнозов и резервов с причиной и подтверждением; после дедлайна запретить обычный сброс из формы редактирования. Для ошибочного вопроса предусмотреть аннулирование без удаления футбольной части прогноза. Изменение этого поведения сначала зафиксировать в ТЗ.

Код: `app/controllers/admin/matches_controller.rb:58`, `app/controllers/admin/matches_controller.rb:131`, `app/views/admin/matches/_form.html.erb`.

Для буквального воспроизведения старого сезона дополнительно нужны источник фактических событий и тот код/скрипт, который записывал вычисленные числа в Sheets. Для реализации уже согласованного нового ТЗ это не повод автоматически возвращать старую схему ЗБ или менять принятые тай-брейки.
