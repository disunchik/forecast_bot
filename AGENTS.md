# Инструкции Codex для проекта `forecast_bot`

## Назначение

Развивать существующее Ruby on Rails-приложение **«AS Roma бот прогнозов»**. Это самостоятельный веб-сервис футбольных прогнозов, не Telegram-бот и не обёртка поверх Telegram. Единственный нормативный источник требований в репозитории: **`docs/REQUIREMENTS.md`**. При расхождении кода и ТЗ сначала выяви расхождение; не меняй согласованное игровое правило молча.

## Контекст и стек

- Репозиторий: `forecast_bot`. Рабочая среда владельца: Windows + WSL Ubuntu, проект находится в Linux-файловой системе (ранее `~/code/forecast_bot`).
- Ориентир стека текущего проекта: Ruby 4, Rails 8.1, SQLite, ERB, Hotwire (Turbo/Stimulus), Rails authentication, Solid Queue, Kamal, PWA-каркас. Перед действиями **проверь реальные версии** через `.ruby-version`, `Gemfile`, `Gemfile.lock` и окружение; не предполагается, что локальная копия идентична ранее переданному архиву.
- Используй существующий Rails-монолит. Не добавляй React, SPA, отдельный API, Redis, PostgreSQL, Kubernetes или сторонний футбольный API без явной необходимости и согласия владельца.
- Время в интерфейсе — **Europe/Moscow**; временные значения в БД храни как корректные timezone-aware даты/время.
- Интерфейс — русский, mobile-first, бордово-золотая тема AS Roma; доступность и удобство важнее декоративных эффектов.

## Как начинать каждую задачу

1. Прочитай `docs/REQUIREMENTS.md`, этот файл и относящиеся к задаче код, миграции, тесты и routes.
2. Проверь `git status` и существующие локальные изменения. **Ничего не перезаписывай и не откатывай без согласования**; не делай вид, что все файлы в чистом состоянии.
3. Кратко сообщи: что уже реализовано, что требует исправления/добавления, какие файлы затронешь и как проверишь результат.
4. Работай небольшими завершёнными блоками. Для каждого — код, тесты, проверка регрессий, затем отчёт. Если задача ясна, реализуй её, а не ограничивайся планом.
5. Не называй функциональность «готовой», если она не проверена. Ранее вручную проверены регистрация, вход, выход и появление админки; остальные сценарии требуют тестирования.

## Безопасность данных и Git

- **Никакого `db:drop`, `db:reset`, `db:seed:replant`, удаления записей, обнуления ЗБ или миграции старых учётных записей на реальной БД без явного разрешения.** Даже в development сперва проверь наличие данных и сделай резервную копию перед опасной операцией.
- `db:migrate` допустим только после изучения миграции и проверки её совместимости с существующей БД. Не правь применённые миграции задним числом: для изменения уже созданной структуры делай новую миграцию.
- Тесты запускай с тестовой БД; не перепутай `development`, `test`, `production`.
- Никогда не публикуй и не коммить `config/master.key`, `.env`, секреты, access tokens, кодовые слова из старого бота, живую SQLite БД или персональные данные пользователей. Если обнаружишь отслеживаемый секрет — сообщи о риске и предложи безопасную процедуру исправления; не раскрывай его содержимое.
- Без разрешения не выполняй force push, rebase чужой работы, удаление веток, широкое обновление всех зависимостей, деплой и операции с production.
- При изменении никнейма используй постоянный `user_id` в связанных записях; не дублируй никнейм в таблицах прогноза/результатов. Доступ к админским действиям проверяй на сервере.

## Предметные инварианты (не нарушать)

- 1 матч прогнозистов = 1 тур/номер в рамках сезона. Номер назначает администратор, может начинаться с **0**.
- Приём прогноза: `[начало матча − 48 ч, начало матча − 2 ч)`. После дедлайна любые изменения запрещены на сервере, а не только скрыты в UI.
- Временный вопрос необязателен для матча, но **обязателен для пользователя**, если добавлен. Первый блок формы — ЗБ, затем временный вопрос.
- У пользователя максимум один действующий прогноз на матч; повторное сохранение до дедлайна заменяет его и обновляет время тай-брейка.
- Лимиты на выбор игрока отдельные для авторов голов и ассистов: по 13 на номера матчей 0–19 и отдельно на 20+. Один выбор игрока на матч расходует одно упоминание, даже если он забил/ассистировал несколько раз. Освобождай лимиты после изменения прогноза.
- ЗБ можно ставить с матча №0; ставка резервируется, не может превышать свободный баланс, после расчёта полностью списывается, бонус ограничен `min(ставка, floor(0.5 × базовые_очки))`. Никаких двойных резервов при конкурентных запросах.
- Чужие прогнозы показываются только после дедлайна. **Чужие ставки и балансы ЗБ скрыты всегда**, включая админские/публичные таблицы (админ видит их только в админке по своим полномочиям).
- После публикации результатов все вычисления, операции ЗБ, таблицы и ачивки согласованы; откат и повторный расчёт не должны удваивать операции/награды.
- Ачивки бессрочные и выдаются в первой версии **вручную администратором**, секретные раскрываются при первой выдаче.
- Фактические футбольные события вводит админ, без футбольного API. Web Push и восстановление пароля как готовый пользовательский сценарий пока отложены.

## Архитектура

- Модели `app/models` отвечают за данные, связи и инварианты.
- Контроллеры `app/controllers` — за доступ, параметры, выбор действий и HTTP-ответы; **не складывай сложный подсчёт очков в контроллеры**.
- Расчёт прогнозов, ЗБ, переходов между таблицами, резервов, откатов и подтверждений — в `app/services` с понятными транзакциями и идемпотентностью.
- Шаблоны `app/views` — ERB; интерактивность добавляй средствами Turbo/Stimulus по мере необходимости.
- Числовые правила расчёта — в централизованных `scoring_rules`, а не в разбросанных magic numbers. Важно сохранять воспроизводимость **уже подтверждённых** результатов при изменении настроек.
- Все критичные админские действия фиксируй через `AuditLog`, включая администратора, цель и причину, если это ручная операция.
- Уважай действующие имена моделей и маршрутов; не переписывай весь проект заново ради эстетики.

## Обязательные тесты

Для любой затронутой механики добавляй сценарии успешного, ошибочного и граничного поведения. Приоритетные сквозные тесты:

1. Регистрация, авторизация по никнейму, права `user/admin`, смена email/пароля, первый вход старого пользователя.
2. Окно `−48/−2 ч`, перенос/отмена, обнуление прежних прогнозов и возврат резерва.
3. Вопросы `choice/text`, несколько правильных вариантов/текстовых ответов, аннулирование вопроса.
4. Валидации HT/FT, счёта 0:0, авторов/ассистов, автоголов, «без ассиста», максимума 8 авторов голов.
5. Лимиты упоминаний по периодам, редактирование до дедлайна, запрет после него.
6. Граничные значения начислений, бонусы 0:0 и «Рома не забьёт», дубли забитых мячей, тай-брейки.
7. Резервирование ЗБ для двух одновременно открытых матчей, округление вниз, исчерпание, конкурентные запросы, отмены.
8. Топ-10/Претенденты, старт после первых десяти матчей, переходы, нулевой матч.
9. Подтверждение, повторное подтверждение, откат, пересчёт нескольких матчей, отсутствие двойных ЗБ и дублирующихся наград.
10. Безопасность: до закрытия чужой прогноз недоступен даже по прямому URL; чужие ЗБ не утекли в HTML, JSON и списки.

Проверяй `bin/rails test` после изменений; по ситуации `bin/rails routes`, `bin/rails zeitwerk:check`, `bin/rubocop`, `bin/brakeman`. Не выдавай прохождение малого числа тестов за доказательство полноты. Если тесты не запускаются, сообщи **реальную ошибку** и что именно не проверено.
